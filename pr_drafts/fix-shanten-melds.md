# CPU の向聴数で副露を数え、色ごとに数えて速くする

ブランチ: `fix/shanten-melds`

## 何が誤りか

`Cpu::Analysis::Shanten.calculate` は手の内の牌を手のすべてとして扱い、面子を 4 つ作る前提で数えます。
副露のある手では誤りで、副露 1 つ＋手の内の 3 面子＋単騎（テンパイ）が 2 向聴になります。そのため:

- 鳴いた後の CPU の打牌（`DahaiSelector`）が、テンパイを崩す牌とテンパイを保つ牌を同じに見ます
  （副露 1 つで `23m 789m 67p 7p 678s`: 6p を切ればテンパイ、7p を切れば 1 向聴なのに、どちらも同じ向聴数）。
- 鳴くかどうかの判断（`NakiJudge`）は、鳴いた後の手を「副露を除いた手の向聴数 − 2」で見積もるので、
  面子を崩すだけの鳴きや、すでに 1 向聴の手の鳴きを「向聴が下がる」と判断します。

あわせて、通常形の探索は手全体を 1 度に再帰で探すので、受け入れの計算（打牌ごとに 34 種を足して数え直す）で
1 手に数十 ms かかります。探索の最良値をクラスのインスタンス変数（`@min_shanten`）に置いているので、
2 つのスレッドが同時に数えると値を取り合います。

## 再現

- `shanten_spec.rb`: 副露 1 つ＋3 面子＋単騎がテンパイ（0）、副露 1 つで 4 面子 1 雀頭が -1、副露 3 つ・4 つの手、
  副露があると七対子・国士無双を数えないこと、`melds:` を省くと門前として数えること
- `tile_evaluator_spec.rb`・`dahai_selector_spec.rb`: 上の手で 6p を切ること（レベル 1〜3）、`seat:` で手の持ち主を指定できること
- `naki_judge_spec.rb`: 副露のある 1 向聴の手では鳴かないこと、副露のある手で向聴が下がる鳴きを選ぶこと

## 直し

- `Shanten.calculate`・`regular_shanten`・`TileEvaluator.evaluate_all_discards`・`count_ukeire` に任意の
  `melds:`（既定 0 = 今までどおりの門前の手）を足しました。副露は面子として数え、七対子と国士無双は副露が無いときだけ数えます。
- `DahaiSelector.select` はその席の副露を数えます（任意の `seat:`、既定は手番の席。`BaseAi` が渡します）。
- `NakiJudge` は鳴く前と鳴いた後の向聴数を、副露の数を入れて数えます。
- 通常形は萬子・筒子・索子・字牌に分け、それぞれの「面子・搭子・雀頭の数の組」を並びごとに 1 度だけ求めて
  （上限つきの表に覚えておく）組み合わせます。探索の手（刻子・順子・雀頭・対子・両面と辺張・嵌張・浮き牌）は
  今までと同じなので、門前の手では同じ値になります。手全体を探す素直な数え方と乱数の手（副露 0〜4、打牌の前と後）
  400 で比べる spec を足しました。インスタンス変数は使いません。

`NakiJudge` の spec「中級は向聴が下がる鳴きを選ぶ」は、今までの数え方に頼っていました（その手のチーは
567p を崩すだけで、向聴は下がりません）。チーで実際に向聴が下がる手に替え、元の手は「向聴が下がらない鳴きは選ばない」の spec にしました。

## 速さ

乱数の 14 枚の手 300 で、全部の打牌の向聴数と受け入れを数える時間: 中央値 63.6 ms → 2.8 ms、95 % 点 191 ms → 5.4 ms、
最大 342 ms → 18 ms。CPU 4 人（hard）の半荘で、1 手の判断の中央値は約 31 ms から約 2 ms になりました。

## 互換性

`melds:` を渡さない呼び出しは今までと同じ値を返します。`Shanten` の内部のメソッド（`explore` など）は無くなりました
（`Mahjong::Cpu::*` は内部 API です）。鳴いた後の CPU は打ち方が変わり、鳴きは減ります。

---

CPU の向聴数が副露を数えておらず、鳴いた後の打牌と鳴きの判断を誤っていた。`melds:` を足して副露を面子として数え、通常形は色ごとに数えて覚えておくことで受け入れの計算を約 20 倍速くした。
